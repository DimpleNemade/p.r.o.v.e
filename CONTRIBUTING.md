# Contributing

This repository is worked on from more than one place, so a few conventions keep `main`
clean and the history readable.

## One change per branch

Never commit directly to `main`. Branch from an up-to-date `main`:

```bash
git switch main && git pull
git switch -c <type>/<short-description>
```

`<type>` follows [Conventional Commits](https://www.conventionalcommits.org/): `feat`,
`fix`, `docs`, `test`, `build`, `ci`, `chore`, `refactor`.

Keep a branch to one logical change. If a task splits cleanly, open separate PRs.

## Commits

- Format: `type(scope): summary` in the imperative — e.g. `fix(api): return 404 for an unknown case`.
- Add a short body explaining *why*, wrapped near 72 columns.
- **Single author identity.** Every commit is authored by the project owner
  (`Dimple Nemade`). Do not add `Co-Authored-By:` or "generated by" trailers.
- Group related file changes into one commit; do not mix unrelated changes.

## Before you push

Run the checks described in
[`docs/12-validation-and-testing.md`](docs/12-validation-and-testing.md). In short, from
the repository root with the virtualenv active:

```bash
# backend
python -m ruff check apps/api services scripts
python -m ruff format --check apps/api services scripts
(cd apps/api && python manage.py check \
  && python manage.py makemigrations --check --dry-run \
  && python manage.py test)
python -m pytest services/forensic-worker/tests -q

# frontend
npm --prefix apps/web run lint
npm --prefix apps/web test
npm --prefix apps/web run build

# docs
python scripts/validate_mermaid.py
```

Run the backend tests from `apps/api/` so Django discovers every app's suite.

## Pull requests

- Target `main`. Fill in the template (`.github/pull_request_template.md`).
- One PR per issue where practical. Put `Closes #<n>` in the description.
- Say what changed, why, and how you verified it.
- If `main` moved, rebase; keep the branch mergeable.

## Numbered documents

Files under `docs/` use a two-digit prefix (`docs/NN-title.md`); ADRs under
`docs/decisions/` and diagrams under `docs/diagrams/` do the same.

- Use the **next free integer**. Never reuse a number.
- State the number you are claiming in your PR description so parallel work does not collide.
- After adding or renaming a numbered document, update the map in
  [`docs/00-programme-overview.md`](docs/00-programme-overview.md) and any inbound links,
  then run `python scripts/validate_mermaid.py`.

## Do not commit

- Secrets or real credentials. `.env` is ignored; keep placeholders in `.env.example`.
- Original or non-synthetic evidence. Development and demos use synthetic fixtures only.
- Generated output (build artifacts, rendered diagrams, caches) unless a maintainer asks for it.
- Another person's unpushed working tree. Commit only your own change.
